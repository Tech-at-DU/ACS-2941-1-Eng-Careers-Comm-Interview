## Overview: The Third Skill (25 min)

Lessons 1-3 were about how you talk through a problem and how you plan a solution. This lesson is about a third, quieter skill: reading code — yours or someone else's — closely enough to trust it. In a live interview, a missed semicolon or a `this` where `self` belongs reads as "didn't check their work," even if the logic was right.

Bugs in this lesson fall into three buckets. Sort everything you find into one of them:

- **Syntax Errors** — the code won't run at all, or throws, as written.
- **Convention Violations** — the code runs fine, but breaks naming/style/best-practice norms.
- **Logic / Interview-Readiness Issues** — the code runs, is even styled fine, but is still wrong, inefficient, or would hurt you in a live interview (an off-by-one, a missing return value that makes the function untestable, a silently swallowed edge case).

That third bucket is the one people miss. "It runs and looks clean" is not the same as "it's right" — and interviewers care about the third bucket more than the other two combined.

**Roadmap — work in this order, don't jump around:**

1. Read the whole snippet once without touching anything. Restate what it's *supposed* to do, in one sentence (same move as Lesson 1).
2. Trace it by hand on a small input. Does it actually produce what you just said it should?
3. **Find Syntax Errors first.** Look for anything that stops the code from running at all: mismatched brackets, wrong keywords, invalid assignment targets, misspelled reserved words. You can't judge style or logic in code that doesn't run.
4. **Then Convention Violations.** Naming casing, spacing, docstring format, `var` vs. `let`, missing `self`.
5. **Then Logic / Interview-Readiness.** Off-by-one bounds, wrong operators (`&` vs `&&`, `=` vs `==`), missing return values, silent failure paths, inefficient approaches.

One more thing to watch for, specific to this lesson: code that looks like it was copied from a tutorial, Stack Overflow, or generated by an AI assistant and never actually reviewed — often has a specific tell, like syntax from one language bleeding into another. You'll see exactly that in Part 2.

### Quick Reference

- **Syntax Error** — throws, or fails to run at all. Quick test: if everything after this line were deleted, would it still crash?
- **Convention Violation** — runs fine, but a reviewer would leave a nitpick on it: naming, spacing, `var` vs `let`, a missing `self`.
- **Logic / Interview-Readiness** — runs, even styled correctly, but still produces the wrong answer, is inefficient, or can't be verified (no return value, an unhandled edge case, an off-by-one).

### Worked Example

Here's the depth and format expected for your write-up in Part 1 and Part 2, on a snippet that isn't part of either:

```javascript
function SumArray(nums) {
  var total = 0
  for (var i = 0; i <= nums.length; i++) {
    total = total + nums[i]
  }
  console.log(total
}
```

*Restatement:* This function is supposed to add up all the numbers in `nums` and return the total.

*Syntax Errors:*
- Missing closing `)` on the `console.log(total` line — throws immediately, nothing after it runs. Fix: `console.log(total)`.

*Convention Violations:*
- `SumArray` should be camelCase: `sumArray`.
- `var` should be `let`.

*Logic / Interview-Readiness:*
- `i <= nums.length` runs one iteration too many — `nums[nums.length]` is `undefined`, so `total` becomes `NaN`. Fix: `i < nums.length`.
- Only `console.log`s the result instead of returning it, so it can't be tested or used by calling code. Fix: `return total;`.

*Fixed:*

```javascript
function sumArray(nums) {
  let total = 0;
  for (let i = 0; i < nums.length; i++) {
    total = total + nums[i];
  }
  return total;
}
```

## Part 1: JavaScript Sample (40 min)

```javascript
function GetEvenNumbers(numList) {
  var results = []
  for (var i = 0; i <= numList.length; i++) {
    if (numList[i] % 2 = 0) {
      results.push(numList[i])
    }
  }
  console.log(results)
}

GetEvenNumbers([1, 2, 3, 4, 5, 6])
```

This is supposed to return the even numbers from `numList`, in order.

1. **Solo (15 min):** find every issue and sort it into Syntax / Convention / Logic-Readiness. Write down where each one is and how you'd fix it.

Did they catch anything in the Logic/Interview-Readiness bucket that you missed?
1. **Fix it (10 min):** individually, write the corrected version.

## Part 2: Python Sample (40 min)

```python
class Queue:
    def _init_():
        this.items = []

    def enqueue(item):
        "Add item to the back of the queue"
        this.items.append(item)

    def dequeue():
        "Remove and return the item at the front of the queue"
        if len(this.items) = 0:
            return none
        return this.items.pop(0)

    def size():
        return len(this.items)

q = Queue()
q.enqueue(1)
q.enqueue(2)
print(q.dequeue())
```

Same process as Part 1 — solo, sort into the three buckets, partner exchange with PR-style comments, then fix it. A few things to specifically watch for here: this snippet has syntax from a different language bleeding through in more than one place (the note from the Overview). Once it runs and is styled correctly, also look at what `dequeue` does with an empty queue, and how `pop(0)` on a plain list behaves as the queue grows — both are Logic/Interview-Readiness, not syntax or style.

## Restate & Verify (25 min)

For **both** of your fixed functions:

1. Restate in one sentence what it does now that it's correct (Lesson 1 skill).
1. Write 2-3 test cases (a normal case, an edge case) that would catch the bugs you just fixed if they came back. You don't need to write a full test framework — a few `assert` statements or manual calls with expected output are enough.

This is the same question Part 1's JS sample raises structurally: a function you can only verify by eyeballing `console.log` output isn't done. If you can't write a test for it, that's itself a Logic/Interview-Readiness issue.
